## 通用模块 → 前端：建议替换正文

### 位置与职责

| 位置 | 职责 | 传统 |
| --- | --- | --- |
| `app/pages/`、`app.vue` | 路由与应用入口、界面组合、交互绑定 | 负责接入参数、组合业务能力与 UI；查询编排、业务操作及状态转换由相应业务模块封装 |
| `app/components/` | UI 组件及其专用实现 | DOM、焦点、滚动、视口等交互就近管理；组件专用实现显式导入，共享业务状态及操作通过业务入口使用 |
| `app/features/` | 按业务组织查询、状态、操作及协作逻辑 | 对外提供明确入口，内部实现显式导入；按职责和生命周期选择 store、composable 或普通函数 |
| `app/composables/` | 全站通用的响应式、上下文及生命周期能力 | 保持公共入口明确；业务或组件专用实现归所属模块，内部辅助实现不加入全局自动导入清单 |
| `app/utils/` | 全站通用工具逻辑 | 不依赖 Vue/Nuxt 上下文，不调用 composables；不隐式读取配置，所需配置及环境能力由调用方显式传入 |

业务模块不要求再建立一套按 composables、utils、services、stores 划分的子目录。小模块保持简单，独立职责或生命周期确实需要时再拆分。业务 store 随所属业务组织，不要求统一位于 app/stores。

跨业务模块通过明确入口协作，避免依赖彼此的内部实现。业务模块需要组件能力时，由调用方提供必要接口；具体组件实例和 DOM 的生命周期由组件管理。

模块之间共享的跨端类型、校验与规则沿用 server/shared 的归属；仅供前端业务内部使用的类型与实现就近维护。

### 状态管理

需要共享或统一管理生命周期的客户端业务状态，可由 Pinia store 管理。Store 封装相关派生状态、业务操作及状态转换，并明确创建、复用、重置和清理规则。

Store 可以通过 API 能力组织请求、维护操作顺序与恢复逻辑；服务端资源的查询缓存和失效刷新复用已有同步机制。需要同时保留本地编辑状态与云端快照时，应明确两者的含义、版本及合并关系。

页面或交互会话独有的业务状态可由业务 composable 管理。DOM、编辑器实例、焦点与滚动等交互状态由组件或其内部实现管理。

业务状态通过明确操作维护。表单输入等允许直接绑定的状态应明确范围；涉及多项状态的一致性、权限变化、异步结果接纳或恢复的转换，集中于所属业务操作。

身份变化、业务对象切换和实例退出时，应按各状态的生命周期清理或释放。共享状态不依附于第一个调用组件的生命周期，局部订阅与交互也不得因共享 store 存活而遗留。

### Composable 的初始化与拆分

使用组件注入、生命周期钩子或 Nuxt 应用上下文的 composable，应在对应上下文有效时初始化；可以在组件 setup 的同步阶段调用，也可以在有效上下文中的其他 composable 初始化过程中同步组合。后续事件或异步回调复用初始化时取得的能力，并遵守其生命周期与运行环境约束。

目录位置不改变上下文要求。业务入口内部的上下文获取与生命周期注册应在有效阶段完成，明确异步准备的等待方式，避免调用方靠猜测初始化顺序使用模块。

Composable 是逻辑封装形式，不要求每个逻辑单元单独成文件。拆分应具有明确的职责、生命周期或复用价值；只有一个调用方不直接决定是否拆分。仅供内部使用的实现就近放置，不因单独成文件而成为公共入口。

## 前后端协作：建议补充的正文

页面与组件通过业务入口使用查询及操作能力。业务入口组合状态、查询与操作，通过统一 API 能力访问服务端；公共 UI 与工具按需使用，不要求所有展示逻辑经过业务模块。

请求与状态转换的协调由所属业务模块负责，具体控件绑定、表单展示、焦点与滚动由 UI 层负责。模块间应明确成功、失败与处理中状态的返回方式，以及提示、确认和导航的负责人，避免同一次操作重复处理。

服务端承担最终输入校验、身份认证与权限判定。前端身份与权限状态用于界面呈现和交互判断，不替代服务端约束。

认证能力与请求传输之间应保持明确的依赖方向；登录、退出和统一错误处理的组合不得形成循环初始化。

## 数据更新：建议补充的正文

业务查询入口负责资源标识、请求参数、加载状态及订阅范围的装配，公共同步机制负责查询复用、失效刷新和生命周期衔接。页面使用业务查询入口，避免重复维护同一资源的查询装配逻辑。

服务端查询快照、本地编辑状态、尚未确认的操作与操作回执应区分含义，并明确各自的维护者。业务状态可以保存流程需要的云端快照，但应规定版本判断、结果合并与过期响应处理，避免同一状态由多个互不协调的副本维护。

变更通知用于触发资源刷新，复用既有通知与查询机制。操作回执需要即时推进业务状态时，由所属模块按既定版本和合并规则接纳；不得绕过已有的跨页面通知流程。

身份变化或业务对象切换后，旧请求、上传回调和其他延迟结果须按当前作用范围校验后接纳。通知遗漏、重连及时间变化相关资源的恢复与刷新策略由同步机制和相应业务入口共同落实。

## SSR 水合：建议补充的正文

SSR 请求使用各自的应用上下文与业务状态；用户身份、权限及用户相关可变数据不得通过模块级变量跨请求共享。浏览器中的共享状态也应具有明确的身份与业务对象范围。

参与首次渲染的数据应沿用现有查询、水合与时间上下文机制，保证服务端输出与客户端首次渲染一致。迁移模块位置或改用 store，不得改变状态键、序列化或初始化语义。

DOM、File、编辑器实例、上传驱动等浏览器运行时对象按所属模块生命周期管理，不混入需要序列化的页面状态。客户端副作用在适当生命周期启动，并在作用范围结束时释放。

身份初始化与同步保留明确的数据来源及更新方向。若改变 cookie 与业务状态之间的关系，应先规定 SSR 初始化、浏览器接续、退出与跨标签页变化时的行为。

## 候选规则的核定清单

人类采纳候选正文时，除文字完整性外，还应核对下列可观察边界；详细后续计划见 [SID#0.1.TMP-CONTENT-UTILS-REFACTOR](TMP-CONTENT-UTILS-REFACTOR.md)。

| 主题 | 核定问题 |
| --- | --- |
| 状态生命周期 | 查询缓存、共享业务状态、页面会话和 DOM／编辑器状态是否各有唯一维护者；共享 store 是否独立于首个调用组件，局部订阅是否随所属实例释放；身份或对象切换后的旧结果如何拒绝 |
| 用户身份 | cookie／`useAuth` 是否仍是唯一身份事实源；用户相关可变状态是否按 SSR 请求隔离；401、退出和跨标签页变化是否保持明确依赖方向，不形成 API/auth 初始化循环 |
| 数据更新 | 服务端快照、本地编辑、pending 操作与操作回执是否区分；通知是否只承担失效和恢复触发；回执合并、版本判断及 owner／generation 检查是否明确，未以页面局部 refetch 替代同步 |
| SSR 水合 | 首屏数据、身份视图和时间上下文是否一致；哪些状态由 payload 延续；普通 `ref` 是否被误写为自动水合；`File`、DOM、编辑器及上传驱动是否排除在序列化状态之外 |

每项规则应能追溯到实际 owning code，并与工程指令和可观察行为一致。总体 DESIGN 只保留全站共用机制，具体 Content 状态、操作和测试命令归所属领域及 workflows；候选目标与当前实现不一致时必须显式标记，不能将设计采纳直接写成代码已验收。
