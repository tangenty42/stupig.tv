## 目标与范围

重构后，页面通过明确的业务入口取得状态和操作；修改某个业务时，相关逻辑可以在所属模块中找到。组件内部实现、业务模块与全站共用能力有清楚的边界。

本次重点：

- 整理已有拆分，收回仅供内部使用的入口，清理无用包装。
- 将页面中的查询编排、业务操作和状态转换提取到所属业务模块。
- 保留有明确职责或生命周期价值的内部拆分，减少调用方需要理解的细节。

首个交付范围为 content 的目录归属、公共查询与编辑页入口；随后整理账号模块。此次重构以保持既有业务行为为前提，不增加 UI 或改变权限、草稿协议、上传协议及服务端 API。基础设施、数据库结构与后端模块重组不在本方案范围内。

## 目标组织

下面是候选路径，用于核对归属。实际文件名与内部拆分可以在实施时按职责调整。

~~~text
app/
├── pages/                         # 路由入口与页面组合
├── components/                    # UI 组件及组件专用实现
│   ├── MyContent/
│   │   ├── Markdown/              # 编辑、搜索、滚动、预览等内部实现
│   │   └── Attachment/            # 附件 UI、图片编辑及其内部实现
│   └── MyAccount/                 # 登录注册、资料等账号 UI
├── composables/                   # 全站通用的上下文与响应式能力
├── utils/                         # 全站通用工具
└── features/
    ├── content/
    │   ├── stories.ts             # 档案查询入口
    │   ├── editing.ts             # 编辑会话入口
    │   ├── draft.store.ts
    │   ├── attachments/           # 附件业务能力
    │   └── uploads/               # 上传状态、操作及内部实现
    └── account/
        ├── auth.ts                # 身份与认证相关入口
        └── profile.ts             # 资料、安全与会话相关入口
~~~

组织约定：

- features 按业务聚合，内部可以使用 store、composable 和普通函数；不要求每个业务再建立一套按技术类型划分的子目录。
- 组件专用的视口、DOM、焦点、滚动和显示偏好逻辑与组件就近放置。跨组件的业务状态与操作归业务模块。
- 全站共用的 composables 保持少量明确入口；业务模块与组件内部实现通过显式导入使用，不加入全局自动导入清单。
- 跨业务模块通过明确入口协作，避免引用彼此的内部实现。业务模块需要操作编辑器时，由调用方提供必要的窄接口，不依赖具体 Vue 组件实例类型。
- 业务专用工具随所属业务或组件整理；跨端规则仍由 server/shared 承担，迁移前端代码不复制这些规则。
- 业务 store 迁入所属 feature 后，不再要求 Pinia 定义统一放在 app/stores。迁移阶段逐个更新消费者，不长期保留只有转发作用的旧路径。
- 测试跟随所属模块；文件名、公共导出与自动导入行为一并核对。Nuxt 生成文件由框架生成，不手工修改。

## 状态与操作的归属

| 内容 | 拟定负责人 | 关键边界 |
| --- | --- | --- |
| 服务端资源的查询快照、共享请求与失效刷新 | 业务查询入口组合现有 useSyncedData | 页面不重复装配资源键与查询；保留现有缓存、通知及水合语义 |
| 草稿文本、编辑权状态、操作顺序、恢复内容 | 草稿 store | 区分本地编辑状态与已确认云端快照，统一管理状态转换 |
| 上传进度、准备与执行、暂停取消、身份变化清理 | 上传业务模块及 store | 保留现有资源版本合并和异步结果校验；File、SDK 对象等保持客户端运行时归属 |
| 一次页面或交互会话独有的业务状态 | 业务 composable | 生命周期由该实例管理；无需为局部状态强行引入全局 store |
| DOM、编辑器实例、焦点滚动及纯展示交互 | 组件及其内部实现 | 业务模块取得必要能力接口，组件负责实际 DOM 操作与释放 |
| 登录身份及其同步 | 账号模块，首轮沿用现有 cookie 语义 | 不增加与 cookie、查询结果互相复制的另一套独立身份状态；服务端继续负责最终授权 |

Store 可以调用 API、组织异步操作并维护业务状态；这些能力不等于必须再建立一套查询缓存。需要持有云端快照的编辑或上传模块，应明确快照、未确认操作与版本合并的关系。

## 实施顺序与验收

### 第一阶段：整理 content 已有模块（已验收通过）

逐个迁移草稿、上传、附件及组件专用实现，更新生产代码、测试与类型引用。先保持既有接口与行为，再清理确认无用的导出；记录暂未迁移的业务专用工具。

完成条件：模块归属清楚，迁移的内部实现不再依赖旧路径或全局自动导入；相关测试、lint 与类型检查通过。移动不能改变 store 标识、状态键、组件名称或路由语义。

实施结果：

- 草稿、编辑会话、附件与上传模块已迁入 `app/features/content/`；上传 runtime 同步迁入所属模块，底层纯工具暂留 `app/utils/content/`。
- Markdown 与图片编辑器的状态、视口、搜索、滚动和预览生命周期实现已移至对应组件旁，通过显式导入使用。
- Nuxt 组件发现已限定为 Vue SFC；源码与重新生成的主应用、组件测试组件声明均不再包含上述内部 TypeScript 模块，旧 stores/composables 路径已清空。
- 未使用的 useAttachmentWorkspace 包装已移除；createAttachmentWorkspace 作为附件模块内部入口保留。
- Store ID、Nuxt 状态键、路由、组件名称及业务逻辑未改动。应用单测、组件测试、 lint 与 Nuxt typecheck 已通过，具体数量见任务交付说明。

### 第二阶段：收敛 content 页面入口（已验收通过）

- 先独立提取三个页面重复的档案列表查询至 `stories.ts`，统一资源标识、加载状态与订阅的装配方式；保留现有状态键、资源键以及 `useSyncedData` 的共享和水合语义，不为查询新增 store。
- 再精简 `editing.ts` 的入口接口：移除确认未被实现读取的参数；以明确回调表达编辑器能力，避免依赖具体 Vue 组件实例类型。移除参数时逐项核对页面查询是否仍有其他作用。
- 编辑入口随后组合草稿、查询及附件业务能力；页面保留路由参数接入、模板绑定和必要的组件交互。
- 入口须同步取得 Nuxt/Vue 上下文并注册生命周期，再通过 `ready` 等待异步查询；不得把顶层 `await` 后创建 composable 的现有顺序直接搬进普通异步函数。
- 保留页面切换后的状态隔离、编辑权失效后的禁写、离开时的收尾，以及旧异步结果不得写入新会话的约束。
- 上传完成后的正文插入由明确操作协调，保留身份、页面存活和写入许可检查；行为测试覆盖身份切换、页面退出及编辑权换代后的迟到结果，并补验页面切换、SSR 水合和订阅释放。

完成条件：页面无需自行组织草稿命令和公共查询订阅；查看编辑入口可以定位状态与操作的负责人。业务入口内部继续依托现有模块，避免把全部实现堆进单个入口文件。

实施结果：

- 新增 `stories.ts`：三个页面通过同一入口复用原有 `content_stories` 状态键、加载键、资源键及 `useSyncedData` 行为，阅读页的单篇正文查询也由该入口负责；未新增查询 store。原先切取页面源码执行的查询测试已替换为 404、暂时失败及切换档案后迟到结果的直接行为测试。
- `useStoryEditing` 同步创建档案查询、草稿 store、附件面板和编辑会话，并以一个 `ready` 等待初始查询；`useAttachmentPanel` 同样改为同步返回控制器和 `ready`。
- `editing.ts` 不再依赖具体 Vue 编辑器实例类型；页面仅提供引用变更应用与 Markdown 插入两个窄回调。未被实现读取的 workspace、title_reference_version、markdown_config、new_markdown 参数已删除。
- `content_titles` 页面查询没有读取方，且草稿引用换代由草稿快照版本驱动，故一并移除；真实浏览器中的跨浏览器标题改名与草稿引用重写场景已通过。
- 上传完成后的正文插入已移入编辑会话；接纳前同时检查页面会话、身份和捕获的写入许可。单元测试覆盖正常插入、身份切换、页面退出、替代编辑会话及尚未建立 story 的情况。
- 应用单测、组件测试、lint、Nuxt typecheck 及五个隔离浏览器场景均通过，具体数量见任务交付说明。

### 第三阶段：整理账号与身份（独立补验通过，已收尾）

- app.vue 通过账号入口与组件使用登录注册能力；身份同步在应用范围内保持明确的初始化与释放位置。
- 整理登录成功、退出、跨标签页变化、资料与权限刷新，保留当前 cookie 语义及刷新策略。
- 个人资料页按资料编辑、账号安全和会话管理提取业务操作及对应 UI。
- 梳理 useAuth 与 useTrpcClient 的依赖：当前传输层需要使用退出能力，账号模块调用 API 时须避免循环初始化。先保留既有底层认证通道，再按明确依赖进行整理。

完成条件：公共框架不再承担登录注册业务流程；账号状态和操作有明确负责人。账号切换、401 和跨标签页变化不会留下旧身份状态或重复订阅。

本阶段不预设必须新增身份 store。如果后续选择由 Pinia 管理身份快照，应另行明确 cookie 与 store 的映射、SSR 初始化和清理机制，并提供相应验证。

实施结果：

- 新增 `features/account/auth.ts`，在不引入身份 store 的前提下组合现有 cookie 身份、`auth_user` 资料及权限刷新和登录注册操作；`app.vue` 仅初始化应用级身份入口并挂载账号组件，不再包含表单、验证码或认证 API 编排。
- 登录注册 UI 已迁入 `MyAccount/AuthDialog.vue`，保留原表单 ID、文案、校验、验证码与成功关闭行为。登录身份仍由 `useAuth` 负责，`useTrpcClient` 继续只依赖该底层通道，账号 feature 不进入传输层，未形成循环初始化。
- 数据同步插件改为直接使用 `useAuth` 提供的 cookie ref 与远端退出处理；同步 transport 仍按 Nuxt 应用单例初始化，并由既有应用卸载钩子释放。资料及权限刷新继续复用 `auth_user:<id>`、轮询和通知语义。
- 新增 `features/account/profile.ts`，集中资料查询、资料编辑、密码与手机号安全操作以及登录会话查询和撤销；保留 `profile`、`profile_sessions` 资源键与既有 Nuxt 状态键。个人资料页缩减为路由、SEO 和三个账号组件的组合。
- `MyAccount/ProfileOverview.vue`、`ProfileSecurity.vue` 和 `ProfileSessions.vue` 分别承载资料概览与编辑、账号安全和会话 UI；组件专用的表单实例、滚动、筛选和确认交互留在组件内，API、同步和 pending 状态由账号 feature 负责。
- 传输层原先用全局布尔值永久抑制后续 401，首次 Promise 修正仍错误共享跨 SSR 请求的任务；补验修正后以 `NuxtApp` 为键保存并发任务：同一应用实例内合并，不同 SSR 请求隔离，任务完成后允许后续 401 再次触发退出。
