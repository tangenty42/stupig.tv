# 『权威文档』宪章

**本文档是仅由人类创建及维护的『权威文档』，禁止 Agent 任何形式的直接修改。**

对于任何此类『权威文档』：

- 如果 Agent 发现『权威文档』中任何内容与直觉、实际实现或『非权威文档』发生冲突，应以『权威文档』为准；
- 如果 Agent 认为『权威文档』中任何内容违反直觉或对其抱有疑问，请向人类提问，而非猜测或默认某种情形；
- 如果 Agent 想要修改本文档，应向人类提供建议，而非直接修改。

# 『Swordoc』机制

此目录下的所有文档遵循『Swordoc』机制：

## 目录结构

文档以逻辑上的层级关系组织，体现为类似这样的目录结构：

```text
docs/
├── README.md
├── 0_overall/
│   └── 0_story_background/
├── 1_workflows/
│   ├── 0_encounter/
│   ├── 1_fall_in_love/
│   └── 2_get_married/
└── 2_domains/
    ├── 0_spice_and_wolf/
    │   ├── 0_holo/
    │   └── 1_lawrence/
    └── 1_sword_art_online/
        ├── 0_asuna/
        └── 1_kirito/
```

以上仅为示例。实际组织方式可灵活多变，但遵循如下规则：

- 文件夹名称格式：`<index>_<description>`，其中 `<index>` 为从 0 开始编码的序号；
- 顶层固定有 3 个文件夹：
  - `0_overall` 包含记录项目背景、架构、依赖和传统的综合性文档；
  - `1_workflows` 包含描述开发、测试、部署、恢复等工作流程的文档；
  - `2_domains` 包含其他按具体业务功能、模块组织的详细文档。
- 每个文件夹下可有如下 5 种文档：
  - `LAW.md` 为『权威文档』；
  - `DESIGN.md` 为『权威文档』；
  - `AGENT.md` 为『非权威文档』；
  - `AGENT-DESIGN.md` 为『非权威文档』；
  - `TMP-*.md` 为『非权威文档』；
  - 以上 5 种文档的具体分工见下一部分。
- 顶层固定的 3 个文件夹分别覆盖 3 个不同维度，属并列关系，其包含的文档内容可相互补充；
- 其他同级目录下的文档也可能存在单向依赖或相互补充的情况；
- 祖先目录下的文档内容自动适用于其子目录，子目录下的文档可对祖先的文档内容进行补充；
- 文档内容之间如有表述冲突，应由人类明确裁定；
- 『权威文档』尽量不要依赖或引用『非权威文档』，如果非要，需在对应『权威文档』及『非权威文档』的文档头明确注明；
- 其实也没那么复杂，你可能看不太懂上面这一大堆话，但是你看目录名称及结构，一目了然、不言而喻。

## 『Swordoc ID』

此目录下的所有文档或文件夹都通过『Swordoc ID』简略表示。按照如下方式，可将文档路径转换为『Swordoc ID』：

- 以 `docs/` 为根目录表示文档路径；
- 省略路径结尾的 `/` 并将路径中所有 `/` 替换为 `.`；
- 文件夹只留下 `<index>`、省略 `_<description>`；
- 省略所有文档的 `.md` 扩展名；
- 加上 `SID#` 前缀。

示例：

| 路径示例 | 对应『Swordoc ID』 |
| --- | --- |
| `docs/2_domains/LAW.md` | `SID#2.LAW` |
| `docs/2_domains/1_sword_art_online/DESIGN.md` | `SID#2.1.DESIGN` |
| `docs/2_domains/1_sword_art_online/0_asuna/LAW.md` | `SID#2.1.0.LAW` |
| `docs/2_domains/1_sword_art_online/` | `SID#2.1` |
| `docs/README.md` | `SID#README` |

## 文档分工

以下表格的说明仅供参考。若要进一步了解，请以已有文档作为最佳示例。

| 文档类型 | 权威性 | 维护者 | 主要内容 |
| --- | --- | --- | --- |
| LAW | 权威 | 人类 | 业务要干什么、业务范围与边界在哪，用户能看到或者能做什么 |
| DESIGN | 权威 | 人类 | 数据库结构；代码、设施要怎样组织；有什么传统 |
| AGENT-DESIGN | 非权威 | Agent 或人类 | 同 DESIGN；补充 DESIGN 未覆盖的部分 |
| AGENT | 非权威 | Agent 或人类 | 当前待办、权威文档解读、具体实现决定（补充 DESIGN 或 AGENT-DESIGN 未覆盖的部分）、工作经验、本文档对应的代码基线、当前代码与权威文档的偏差 |
| TMP | 非权威 | Agent 或人类 | 任何内容 |

### 固定文档头

```markdown
# <!-- 文档类型，LAW/DESIGN/AGENT/AGENT-DESIGN/TMP -->：<!-- 文档标题 -->

- 本文档状态：<!-- 本文档状态，DONE (编写完成)/PENDING (正在编写)/BROKEN (亟需修改)/ABANDONED (已废弃) -->
- 覆盖范围：<!-- 描述文档覆盖的功能、模块 -->
<!-- 可自行补充栏目 -->
```

## 文档风格

- 假设读者是智者：无需赘述大伙都知道的事实（如 Nuxt SSR 水合的机制）；可把读者当作刚接手本项目的新人（而非编码新手），写清楚我们自己项目的约定、取舍、例外之类就好；
- 避免随意造词或滥用术语：优先用短语或句子直接说明某个东西是什么、做什么，不要天天造过度压缩、晦涩难懂的词，如写 `同一份共享数据的存放单元：保存所有订阅者和最近一次结果，用第一个订阅者的请求函数发请求……` 而非 `前端一份数据的请求协调者`；需要造词命名时，在首次出现处（或单独的术语表中）定义；行业通用术语可以用，但不要单纯为了压缩字数就滥用；
- 节省读者注意力：善用关联词把条件和例外标出来，避免平铺直叙——条件（若、仅当、只有……才）、例外（但、除……外）、让步（即使……也、无论）、结果（所以、因此、故）等等；如果发现一段话里关联词满天飞、已经产生分散读者注意力的副作用，就应该着手拆句或删减；
- 避免过度的防御语气：如果特别想强调某个正确做法，应着重解释为何这么做、具体怎么做，反例只在容易踩坑时适当补充（点名 ChatGPT 滥用 `不是……而是`、`不代表`、`不能说明`……）。

## 尊重权威，勇于提问

- 尊重权威：做事以人类给出的『权威文档』、明确 Prompt 指令等为主要依据；如果『权威文档』和明确 Prompt 指令发生冲突，请确认人类已经对此非常了解，否则，必要时暂停工作直到得到确认；
- 勇于提问：涉及业务含义、重要设计取舍或规范冲突时勇于提问；认为权威指示有任何不合理、值得改进指出欢迎指出，在人类允许的情况下，勇于破立。

## 习惯做全面的观察与计划

对于某个重要决策，习惯事先考虑其背景、可能引发的实现改动、影响及验证方式，以便做完整的计划：

- 背景：决策来源、佐证材料等；
- 改动：可能引发的代码结构、基础设施等具体实现的变化；
- 影响：可能对业务逻辑、工作方式等引发的短期、长期影响；
- 验证方式：如何验证猜测是否合理、任务是否完成等。

## 维护一致性

- 尽可能维护业务逻辑与具体实现之间的一致性，如果二者不一致，及时提出、供人类决策；
- 尽可能维持各业务模块之间工作范式、心智模型的一致性，例如：如果修改（或创建）一个共有模块可以解决一个普遍问题（或增进复用与一致性），那么在整体结构完整、耦合与复杂度可接受的情况下可优先选择之。
