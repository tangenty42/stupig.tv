# Content 重构执行记录

日期：2026-10-14。实施依据为[附件工作区重构提案](./attachment-workspace-refactor.md)和[正文引用语法](./content-reference-links.md)。

本轮完成可独立发布的引用语法阶段，完整附件工作区重构尚未完成。开始时工作区已有任务暂停、重试、同步等未提交改动，本轮保留这些改动，不把它们计为本轮新增成果。

## 已实现

- `server/shared/content-reference.ts` 提供单一解析、解码、格式化及标题比较入口：显式 `att://` / `content://`，路径尾斜杠归一化，中文和百分号编码处理；兼容类型仅用于转换和切换期间的读取。
- 共享 Markdown 扫描、提取、校验和改写接入新入口；转换和改写保留嵌套标签、尖括号目标和 title 属性，不改动代码及原始 HTML 属性。HTML 原始内容排除规则与编辑器和渲染器共享。
- `rewrite_content_refs` 一步内同时替换、多步按顺序重放。结构服务接入同一实现，修复链式文件移动串改、目录卡片引用漏改及封面连续改写。
- 渲染器支持新语法；拖拽、复制及补全生成同一格式。兼容读取暂时保留，避免尚未执行转换的数据库或旧标签页显示失效。
- 编辑器 `@` 补全合并档案和顶层附件两个固定分区；`att://` 下钻只列直接子项；文件夹光标停在闭括号前；复用自动闭括号。菜单使用 ContextMenu design tokens，文件夹显示下钻指示。
- lint 对缺失附件给出警告，对不存在、自引用或非法档案标题给出错误；scheme 大小写提供快速修复。关闭兼容后，旧引用报错，存在同名目标时提供快速修复。
- 草稿 schema 升为 v3：读取 v2 时转换正文并保留 revision、保存时间和内容，两条引用版本基线记为未知；不删除可恢复草稿。
- `app.content.reference.legacyCompat` 默认开启；保存时先转换旧客户端正文。关闭后返回 `400 LEGACY_REF` 及行号；安全结构化详情经 ApiError、tRPC formatter、客户端普通请求和 XHR 路径保留，未知字段不透传。
- 新增 `pnpm content:refs:migrate`：默认 dry-run；`--apply` 逐篇加行锁重新读取、转换正文、提交后发刷新，不增加正文 revision，可重复执行。报告只含档案 ID、是否变化及引用目标统计。
- 迁移工具随 `maintenance:build` 打包进镜像；部署后在 `/app` 内运行 `node .output/server/maintenance/content-references.mjs`，确认报告后加 `--apply` 执行。应用启动不会自动转换存量正文。
- 新增引用构造清单，登记 `attachment_ref`、`folder_ref`、`story_ref`，测试检查三项格式和解析覆盖；完整方言清单仍可继续扩展。

## 尚未实施与切换条件

| 阶段 | 状态与原因 |
| --- | --- |
| 真实对象存储能力验证 | 待验证：当前部署配置为单个公开桶，endpoint 是 rains3；不能用 S3 mocks 推断真实 OSS 的 CORS、multipart 和跨桶复制兼容性 |
| 私有桶发布 A / 旧密文迁移 / 发布 B | 待实施：没有开发和生产私有桶配置，也没有匿名拒绝、签名 GET、CORS 与复制核对结果；因此保留 AES、密钥和旧密文 |
| 稳定节点、统一 name_key、上传会话、幂等回执 | 待实施，需按主方案在存储验证和私有桶阶段之后推进；旧任务仍是当前写入口 |
| 命名空间 / 标题日志与保存重放、草稿服务端替换 | 待实施，草稿的两条基线目前保持未知，不伪造已重放版本 |
| 独立附件资源、工作区门面、面板及上传适配器 | 待实施；当前附件仍随档案读取，任务 store 和编辑页编排尚未退休 |
| 移除正文附件删除副作用、旧 task API / runner / 表 | 待切换；不能在新入口、迁移和并发验证就绪前移除 |

目前结构服务仍保留既有正文 revision 冲突保护。命名空间日志和保存兜底尚未上线，提前移除 revision 增量会让旧草稿覆盖改名后的正文。只有新的重放协议完成后，才能达到目标方案中的“机械引用改写不抬正文 revision”。

## 后续执行建议

1. 明确实际存储服务及开发、生产私有桶的 endpoint、region、bucket；凭证在环境文件中配置，不写进文档。验证匿名拒绝、CORS、RAM 权限、签名 GET、跨桶复制和大对象分片复制。
2. 按主方案 §10.4 实施发布 A，先生成密文迁移 dry-run 和异常清单，再迁移核对；核对前保留全部旧密钥及对象。发布 B 和保留期清理分别推进。
3. 用通过真实存储验证的上传适配器接入新节点、会话和幂等协议；Uppy 仅在满足 §7.4 且新增依赖单独获批时采用，否则保留自制上传器的字节传输能力。
4. 用真实 MySQL 的并发测试验证上传预约、commit/cancel、正文保存/附件删除、标题级联和响应丢失；随后切换独立资源与工作区，再退休旧任务模型。
5. 转换脚本 dry-run 为零且旧前端兼容窗口结束后，在下一发布周期关闭 `legacyCompat` 并移除临时兼容读取。
