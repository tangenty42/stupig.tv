## 何时迁移、何时移除旧凭据

生产副本预演应在上线前完成，正式迁移必须安排在新应用上线的同一个停写窗口内。顺序是：构建并验证新镜像 → 生产副本完整预演 → 停止旧应用和写入 → 最终备份 → 使用旧源读取凭据和新 OSS 应用凭据执行迁移 → 启动新应用并发布生产函数 → 验收并恢复流量。不能等旧凭据失效后再复制对象，也不能切换指针后继续运行旧版本。

历史迁移的旧源配置来自当时的 `oss.buckets.public/private` 与 `OSS_PUBLIC_*` / `OSS_PRIVATE_*`，目标来自 `aliyun.oss` 与 `ALIYUN_OSS_*`。当前静态资源也已迁入新桶，日常配置不再指向旧源，也不注入旧凭据。恢复或重演历史数据时必须使用受保护的对应源码、源 YAML 和环境备份，不能用当前新桶配置重跑历史旧源复制。密钥不进镜像。

Content 迁移只搬迁档案附件。后续静态迁移已将开发、生产各 13 个头像及图标对象复制到各自新桶，逐对象校验完整 SHA-256 和私有 ACL；新头像写入也已改用阿里云接口。旧源退出日常配置，凭据仅保留在受保护的恢复备份。运行退出与物理销毁是两个阶段，旧源对象及恢复材料仍覆盖回滚保留期，不自动全桶删除。

随后全桶对账与旧删减版 UI 清理已上线 `20261025-e9f50d4e`，当前镜像身份为 `sha256:0d6b0331172631f908d017f189becc3b92ca96d028039574991bad080c5f69c1`，25 项迁移 completed。新增迁移只建立扫描账本；生产首轮检查 405 个引用、313 个当前对象，未发现异常。此次备份在 `.migration-backups/audit-20261025-e9f50d4e/`，SQL 摘要 `1d036caf2be23a4edb18e0f0b3a832d069eeba953a4d52f546a42283b2e48bc4`。详见[全桶对账](storage-audit.md)。

迁移保留已有文件和目录身份，将路径按当前 NFC／大小写规则建立父子关系，并保证此前可解析的附件引用仍指向原 ID。旧 `.good` 机密图片与同名公开图片配对时，为机密行生成独立删减版对象；公开行及其 ID／引用保留，两行不形成后续版本依赖。

普通文件以及 GIF、SVG 等按原始字节复制。支持处理的静态 JPEG、PNG、WebP、AVIF 生成独立原图、AVIF、JPEG fallback 与 LQIP；已经完整的图片模型保留已有编辑结果，半套模型不猜测修补。

旧行存在 `encryption_key` 时才执行历史 AES-GCM 解密：完整认证成功后才能完成目标对象上传。当前 `.good` 表示访问控制，不代表新文件需要 AES 加密。迁移目标使用不可变 key、显式 private，并读回核对大小和 SHA-256 等身份信息。

## 进入维护窗口前

1. 用生产数据的受控副本执行完整预演与迁移；副本数据库、对象目标与生产目标隔离。
2. 记录源码／镜像身份、冻结摘要、配置环境、源桶和目标桶、图片编码器与 profile。迁移重入会拒绝目标桶或编码器悄然改变。
3. 准备可恢复的数据库备份、对象版本清单和旧 AES 恢复材料；按[备份手册](./backup-recovery.md)进行恢复演练。
4. 核对源对象可读、目标桶权限与版本策略、RAM 应用权限、分片签名上传与 CORS、ESA 路由和生产授权回调。当前浏览器不使用 STS 凭据，保留的 `uploadRoleArn` 字段不是迁移或上传的放行条件。
5. 识别旧任务、旧复制过程、新上传活跃会话及未结束图片任务；逐项处理到确定状态。失败或暂停不能自动视作已完成。
6. 安排关闭所有应用写入、worker 和旧清理 cron。迁移工具的 `--maintenance` 不会替你完成这些动作。

NFC／大小写重名、文件作为父目录、非法路径、缺失档案、活跃工作或不完整图片模型都会阻止执行。先修复明确的数据问题，再预演；不自动改名、合并目录、取消任务或丢弃源文件。

## 分阶段执行

以下命令适用于已经选择正确环境的源码工作区；生产推荐使用[维护容器入口](./migrations.md)。阶段顺序相同，只替换命令前缀。

```sh
pnpm migrate --status
pnpm migrate --through 20261024210000_content_cutover_state.sql
pnpm migrate --dry-run --through 20261024210100_content_references.ts
pnpm migrate --maintenance --through 20261024210100_content_references.ts
pnpm migrate --dry-run
pnpm migrate --maintenance
pnpm migrate --status
```

预演输出安全计数、问题码和 scope/node 身份；前置尚未完成会显示 `blocked_by`。不要把早期预演中的后序阻塞当成完整对象迁移通过。原本已悬空的引用保持 warning，迁移不会凭空生成其目标。

对象复制和图片处理在长事务外完成，逐对象回执持久保存；最后在档案事务内提交目录、对象指针、正文、封面、命名空间基线、通知 outbox 与 adopted 回执。旧草稿历史 floor 随命名空间切换推进，不能把缺少可靠基线的旧草稿静默回放到新身份上。

## 中断与结果未知

- 重跑同一冻结版本，按迁移账本复用目标、upload ID 与分片。不要更换目标后继续同一执行。
- Complete 回执丢失但对象存在时读回对账；源身份、目标或摘要不一致则停止。
- upload ID 消失但目标不可见，或出现多个无法辨别归属的 multipart 时，先人工核对，不盲目重建或覆盖。
- apply 结束后的 verify 失败只重验；不要删除回执强迫重做复制。
- 迁移失败期间继续冻结写入。失败信息不应输出原正文、AES key、签名 URL 或原始 SDK 响应。

| 范围 | 应确认的结果 |
| --- | --- |
| 版本 | 全部预期版本 completed，无运行中／失败回执 |
| 目录与引用 | ID 保留、父子关系有效、正文／封面已转换，新增悬空引用为零 |
| 对象 | 目标存在、private、大小和完整摘要正确，源仍保留 |
| 图片 | 原图、AVIF、fallback、LQIP 和删减版各角色正确 |
| 权限 | 匿名／普通／机密权限用户的预览和下载符合当前合同 |
| 云端 | 生产 GET/HEAD/Range、完整下载、缓存 HIT 后撤权通过 |
| 同步与草稿 | 新命名空间下同步正常，旧草稿得到明确冲突处理 |
| 后台 | 上传生命周期、图片、退役、预热及通知无异常积压 |

先启用新应用并完成生产入口验收，再恢复写入。保留回滚窗口内的旧源和迁移材料。迁移前后的业务对象、引用、授权要验证，不以单纯行数相同或 `/healthz` 成功代替。

## 恢复材料与回收

| 表 | 必须保留的意义 |
| --- | --- |
| `content_migration_references` | 原始正文和引用转换备份 |
| `content_migration_scopes` | 源行快照、档案切换状态与结果指纹；可能含历史 AES 恢复材料 |
| `content_migration_objects` | 逐角色源／目标身份、分片、大小、摘要与对象回执 |
| `content_migration_pins` | 阻止旧阿里云源 key 被日常退役扫描提前回收 |

没有通用 down。回退需要对应的数据库快照、旧对象和匹配版本的应用；恢复写入后还要处理新增数据，不能仅把 adopted 或 completed 改回 pending。

旧源退役是独立显式阶段。确认保留窗口结束、无回滚需求后再按精确对象清单处理并释放 pin，不能清空迁移表或递归删除桶前缀。当前日常退役负责正式替换／删除的对象及 ESA 刷新，不是业务回收站。`storage:cleanup --delete` 已停用；上线前停掉旧清理 cron。

隔离演练入口见[测试说明](../development/testing.md)。旧 `content:workspace:plan`、`content:storage:migrate`、`content:private:migrate`、`content:refs:migrate` 均已退休，统一使用上述版本链。
