# LAW：附件

- 本文档状态：DONE
- 覆盖范围：附件列表、各种附件操作、冲突与错误处理

## 概念

一个 item = 一个文件 / 一个文件夹

## 附件列表

- 附件列表包含附件文件和附件文件夹，单击文件夹 items 可展开 / 折叠之；
- 所有附件 items 的显示（详情页、编辑页、冲突 resolve dialog、附件状态变更确认 dialog 等）共用一套组件，样式和整体操作逻辑相同，只是右键菜单等行为有差异；
- Ctrl/⌘ + 单击（或 Shift + 单击；手机可对任意 item 左滑），或鼠标按下框选（手机可从空白处开始拖动）可『选中』附件列表的 items；其中 pending items 和正常 items 多选互斥、子代和父代多选也互斥；
- 双击附件文件 items 可打开或下载（图片可预览）；
- 右键 items 可触发右键菜单；右键空白处也可触发右键菜单；
- 右键菜单是多面派，见机行事，看情况隐藏或 disable 不可用的选项。

### 上传

对有权之人，附件列表上方有个『+』按钮，点击弹出菜单，可选上传文件、文件夹或新建文件夹。

空白处右键（或对文件夹 items 右键）也可弹出含有上述上传操作的菜单；如果是对文件夹 items 右键触发上传，则上传操作以该文件夹为根目录。

还可以拖动上传（拖动到附件列表根目录或特定文件夹，或到 Markdown 编辑器）或粘贴上传（粘贴到 Markdown 编辑器）。其中粘贴上传在正式传输前会弹出更名 dialog，可在上传前修改粘贴图片的文件名。

### 替换

对文件 item 可用，弹出一个对话框，可拖入、粘贴新文件或选择新文件，之后上传此新文件以替代旧文件位置。可选择保留旧文件名称（不保留扩展名：比如旧文件是 `猪头.jpg`，新文件是 `西外.png`，若保留旧文件名称，则替换后文件名是 `猪头.png`）或跟完全随新文件的文件名。

如果发生文件名变更，会自动更新各处的引用，见 `SID#2.4.3.LAW`。

### 改名

右键菜单可操作，无需多言。

不能改文件扩展名；名称大小写不敏感。

会自动更新各处的引用，见 `SID#2.4.3.LAW`。

### 移动

可通过右键菜单或选中 items 后在附件列表内拖动实现。

会自动更新各处的引用，见 `SID#2.4.3.LAW`。

### 删除

右键菜单可操作，无需多言。

若想要删除的文件或文件夹有引用，只会提示、dialog 确认，见 `SID#2.4.3.LAW`。

### 设为机密 / 取消机密

右键菜单可操作。

任何 items（文件或文件夹）都可设为机密。机密文件夹的机密状态会继承给其子代。

将某 item『设为机密』后，其名称会在原来基础上附加 `.good` 后缀（此后缀作为形式后缀，将该 item 标记为机密，不影响文件类型识别等正常业务逻辑），『取消机密』时该形式后缀删除（只是删除该形式后缀带来的机密状态，不影响从祖先文件夹继承的机密状态；另见下文『总而言之』）。

文件夹还可通过直接改名为以 `.good` 结尾的名称来设置为机密文件夹、或删掉 `.good` 后缀来取消机密设置。

#### 总而言之

##### 判定某个 item 是否机密：

- 若同一文件夹里有文件 `<file_name>.good`，则文件 `<file_name>` 是它的『删减版』，非机密，即使它在机密文件夹里（`<file_name>` 本身以 `.good` 结尾时不适用）；
- 其余 items：路径以 `.good` 结尾或包含 `.good/` 的是机密，反之不是。

以上名称比较对大小写不敏感。

##### 其他细节

- 上传时，items 自带的 `.good` 后缀将得到保留并发挥功能；
- 删除 `.good` 后缀成功后，如果某 item 仍因继承祖先文件夹的机密状态而保持机密，则加以提示；
- 改名、移动、删除、替换、上传（尤其是粘贴上传时，可改名）、设为机密或取消机密等操作，如果会让某个 item 因此变成删减版或不再是删减版、或机密状态因此改变，都需弹出附件状态变更确认 dialog（见下）。

### 冲突 resolve

上传、改名（包括粘贴上传、替换、保存图片等时的隐式改名）、移动、删除、设为机密或取消机密等操作时可能出现以下这些冲突：

| 冲突原因 | 可选 resolve 方式 |
| --- | --- |
| 操作的 items 与已有 items 重名（仅限：文件与文件、文件与文件夹或文件夹与文件） | 只重试 / 跳过 / 自动编号 |
| 新 items 名称非法 | 只重试 / 跳过 / 清洗 |
| 其他 | 只重试 / 跳过 |

文件夹与文件夹重名时不算冲突——文件夹重名发生在上传、移动、改名（含各种隐式改名）等操作时，默认行为是合并。新建文件夹则不允许重名。

每次提交时，按以下规则判定和解决冲突：

- 每次判断时，上传预约的 items 都视为已存在；
- 每次操作，用户的 resolve 决定保存在前端，在每次提交时交给后端，多轮提交 resolve 决定可累计；每个 resolve 决定需要匹配对应的 items 方可生效；
- 每一轮判定都假定已预约的 pending items 已存在、且前面各轮的 resolve 方式已经生效；
- 在任何一轮判定中（一轮判定：指扫描一种冲突原因），触发了尚未决定 resolve 方式的冲突、或被『跳过』解决的 items 都不再参与后续判定；
- 一旦出现尚未决定 resolve 方式的冲突，则暂缓整批处理，并弹出 resolve dialog 等待确认。

### 附件状态变更确认

所有冲突都解决后，用整批操作的最终结果与『操作前的状态』对比，若发现有 items 因此 **隐式、间接** 变成删减版、或不再是删减版、或机密状态改变，则暂缓整批处理，弹出附件状态变更确认 dialog 等待确认：

- 每次判断时，上传预约的 items 都视为已存在；
- 对于新出现的 items（来自上传、图片编辑另存等），规定其『操作前的状态』为其上传目标文件夹的一般 item（非删减版、且只继承祖先的机密属性）；例如，如果名叫 `<file_name>` 的某文件本来是上传到机密文件夹，但因为该文件夹下本来有个 `<file_name>.good`，会导致该文件变成删减版而公开——与我们为新出现的 items 规定的『操作前的状态』相比，它变成删减版、且机密属性没有了，所以要弹附件状态变更确认 dialog（`<file_name>` 本身以 `.good` 结尾时不适用）；
- 样式复用 resolve dialog，列出受影响的 items，用 icon 和颜色表达变化；
- 只可『继续』或『取消』；『继续』表示批准当前 dialog 中列出的影响，重新提交后若发现影响与先前判断的不同，则再次弹框；
- 删除附件操作先弹出存量引用确认 dialog（见 `SID#2.4.3.LAW`），再弹出附件状态变更确认 dialog。

在设为机密、取消机密、图片编辑保存为删减版等操作中，若一些 items 被 **显式、直接** 更改机密状态或删减版状态，则不会因此触发附件状态变更确认 dialog；不过若其引发任何 **隐式、间接** 的变化（可能是此次操作直接作用的 items 的状态变化，也可能是并没有直接操作到、但受之影响的 items 的状态变化），则仍然会触发该 dialog。

附件状态变更确认 dialog 以一棵文件树一次性列出所有受影响的 items（不像 resolve dialog 那样分组），并用 icon、箭头和颜色表达各自的变化。
