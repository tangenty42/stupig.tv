# 图片、编辑与删减版

图片是附件行的一种表示。一次上传或编辑产生多个物理对象，但附件列表和 Markdown 中仍只有一个逻辑附件。头像等其他模块不使用本页的 Content 图片模型。

## 图片类型与对象角色

静态 JPEG、PNG、WebP、AVIF 的新任务使用 OSS 图片处理；GIF、SVG 等其他图片按原始字节存储，浏览器支持时可以预览，但不压缩、不进入画布编辑。处理管线验证字节、单帧、尺寸和资源预算，不能靠改后缀绕过限制。以下为当前代码行为，生产仍须随 PR 部署验收；正常与删减展示统一为 WebP Q100，保留 JPEG 兼容回退；新上传仍接受 AVIF 输入。旧任务须在维护迁移前完成或显式取消，不能静默重解释其编码合同。冻结迁移实现与 AVIF profile 1 不变。

### 上传前门禁

处理图片最多 **20 MiB**，宽、高均不超过 **4096px**，总像素不超过 **9,437,184**。这是当前应用的输入资源预算，并非 WebP 格式的最大尺寸。OSS 旋转操作仍限制输入宽高；在重新测量大图资源峰值前保留双边 4096px 门禁和现有像素预算。限制由 `config/app-settings.yaml` 的 `app.content.image.upload*` 生成，前后端共用。

选中后先展示现有文件列表准备行，只读取 PNG／JPEG／WebP／AVIF 的尺寸头，不进行全文件哈希或像素解码。超限、损坏或无法识别的头直接写入该行既有『准备失败』错误栏；整批不受理、不启动字节上传，可用现有『取消准备』撤回。普通文件不新增读取成本；替换、另存为及删减编辑的导出文件也经过相同门禁。服务端受理再次核对声明大小，上传封存后的实际字节还会验证格式、帧数、尺寸、SHA-256 及来源版本，不信任浏览器声明。

| 字段／角色 | 含义 |
| --- | --- |
| `object_key` | 当前正式内容；处理图片指向当前 WebP，原图直传类型指向原始对象 |
| `original_key` | 本附件自己的初始归档，用于下载原图和回退画布 |
| `display_key` | 当前正常版本的展示、普通下载与继续编辑输入 |
| `fallback_key` | 从最终 WebP 生成的持久化 JPEG 回退 |
| `source_display_key` | 正常覆盖时记录的来源快照身份，不是新附件的原图继承关系 |
| `redacted_display_key` / `redacted_fallback_key` | 同一行的可公开删减表示，首次保存时才建立 |

业务字段、产物元数据、读取角色及编辑来源统一使用 `display`／`fallback`，不使用格式名。后缀、MIME、Accept 协商和普通下载名由[图片格式映射](../../../server/shared/content-image-format.ts)集中描述；实际 WebP／JPEG 编解码保留在编码器内。以后更换格式无需再改业务列名或读取协议。

正常与删减表示各有自己的 revision、尺寸、大小、摘要和 LQIP。无机密读取权限时，服务端不把正常版本的图片元数据或 LQIP 一并下发。

原图归档保留上传字节，不保证源文件本身是无损编码。上传输入先进入 `content/att/staging/`；正式原图和图片产物分别位于 `content/att/originals/` 与 `content/att/images/`。这些前缀不是用户路径，改名不改对象 key。

## 处理与发布

图片尝试先记录任务、尝试身份及来源，生成 WebP，再从该 WebP 生成 JPEG 与小尺寸 LQIP。首次上传还把原始字节独立归档。对象私有权限、身份、大小与摘要经过验证后，才允许在数据库事务中采用一组完整角色。

新任务在 intent 中冻结 `processor: oss` 和 cloud profile 3：WebP Q100、JPEG Q85、24px JPEG LQIP Q40。后台使用 OSS V4 请求头鉴权的 `processObjectSave`（`sys/saveas`），在 OSS 内直接持久化 WebP／JPEG；LQIP 使用有界 IMG GET，仍作为现有数据库字段保存。JPEG／LQIP 均读取已确认版本的最终 WebP。编码参数与先前中转方案相同，不另增 profile 或修改冻结迁移。没有浏览器转换 URL 或任意参数签名接口；用户继续走现有 Content／ESA 成品读取授权。本地 WebP 测试／维护编码使用 effort 4；OSS 没有对应的已验证 effort 参数。[Safari 14 才新增 WebP 支持](https://developer.apple.com/documentation/safari-release-notes/safari-14-release-notes)，按项目 Safari 13.1 起的兼容范围继续保留 JPEG 协商回退。`contentImages.profile` 仍保存冻结迁移所需的 AVIF profile 1；当前本地与云端处理均使用 `contentImages.cloud.profile` 的 WebP 合同，不会在关闭云端编码时改回 AVIF。

直接持久化前逐次验证目标桶为 private、来源版本／ETag／大小／ACL 未变且尝试目标不存在，成功后显式钉住对象 private ACL。每份成品只作一次有界回读，核对真实字节的 SHA-256、格式、尺寸、大小和版本；服务器不再上传转换后的图片字节。SDK 的原生保存接口不能传入来源 If-Match，故仅使用尝试拥有的不可变来源，保存前后仍核对完整版本身份；JPEG／LQIP 生成后再次验证全部角色。响应丢失、取消或租约失效不自动重发 POST，也不降级回中转；未采用及迟到对象继续由既有尝试账本负责。

[原生保存继承桶 ACL，不能自定义对象 ACL](https://help.aliyun.com/zh/oss/user-guide/sys-or-saveas)，所以 private 桶是创建前置条件。它也不复制源对象的 Cache-Control；浏览器的 `private, no-store` 继续由 OSS 签名读取的 `response-cache-control` 与 [ESA 出站响应规则](../../deployment/esa.md#esa-到客户端响应头)保证，不为补元数据自拷贝产生额外历史版本。RAM 仅补指定桶的 `GetBucketAcl` 及 staging／images 来源前缀的 `PostProcessTask`，目标仍使用原有 PutObject 权限，见 [RAM 清单](../../deployment/ram.md#图片原生持久化权限)。

失败、取消或过期尝试不覆盖正式行；旧尝试的迟到写入由账本继续跟踪和清理。对象发布同时登记预热及旧对象退役意图，见[对象生命周期](object-lifecycle.md)。

现行 app 模式下，上传封口／重试提交 queued 或 ready 图片状态后立即唤醒本进程后台，避免空闲任务固定等待下一次五秒扫描。正在执行时的重复提示合并为一次后续扫描，仍遵守资源槽、领域租约和并发限制；周期扫描保留为兜底。独立 worker 不接收此进程内提示，调度边界见[后台工作](../background-jobs.md#调度和退出)。此优化只减少任务发现等待，不省略转换、归档或校验，也不承诺完整上传链路的固定时延。

## 画布与保存

普通编辑和删减编辑共用全屏 `ImageEditor`。同一画布提供画笔／橡皮擦、旋转、裁剪、撤销／重做和视口操作，没有平移／裁剪／画笔三套互斥编辑模式。

- 桌面端 Ctrl + 滚轮缩放；Ctrl／⌘ 或空格 + 拖动平移画布。裁剪框靠边框和手柄移动／调整，不再通过修饰键拖动整个框内区域。
- 双指缩放／平移在整个画布区域生效，不仅限图片像素范围；双指开始不能重置已有裁剪区域。
- 『适应窗口』允许小图放大；『原始比例』恢复 1:1，旁边百分比显示当前视口倍率。视口缩放不改变导出尺寸。
- 橡皮擦只修改当前编辑笔迹层，不能恢复已烘焙到源 WebP 的遮挡。裁剪／旋转属于编辑历史，撤销／重做按历史可用性禁用。
- 『应用裁剪』立即进入本地编辑历史；『回退原图』有确认，读取本行归档、替换画布并重建本地编辑基线。二者都不等于已经保存。

普通编辑默认『覆盖』，也可『另存为』。覆盖时名称输入仍显示原名称并禁用，避免布局跳动；另存为只修改主体名称，固定 `.webp` 后缀。保存确认明确模式及目标。

| 保存方式 | 行与归档 |
| --- | --- |
| 覆盖 | 更新原行的正常 WebP／JPEG，保留该行原图归档 |
| 另存为 | 创建独立新行，将首次输出 WebP 另作自身归档；新行不依赖源附件 |
| 编辑删减版 | 更新当前行删减 WebP／JPEG，不改正常版本或归档 |

回退原图只改变当前前端画布，所有保存方式都可以使用。取消编辑不会删除已保存版本；没有本行可读归档时不能执行回退，也不会追溯其他附件的原图。

## 删减版的生命周期

『编辑删减版』从机密图片菜单进入，固定保存到当前行；普通编辑的保存模式中没有『创建删减版』。已有删减版时以其当前 WebP 为输入，否则以正常 WebP 为输入。

删减版初始不存在，首次保存才创建两个 key；没有独立附件行或额外原图档案。『删除删减版』经确认清空删减字段及元数据、推进版本，并登记旧对象退役。编辑器不提供另一套『恢复正常版本』删除入口。

列表和引用补全仅将『机密且自身存在删减版』的行标蓝，普通附件使用正常图标与颜色。Markdown 的删减展示也只读取同一 row 的删减字段，不再按同名 `.good` 文件或历史 `redaction_source_id` 配对其他附件。

机密切为公开会保留删减 key，重新设为机密可以再次使用。覆盖／替换正常图片遇到已有删减版时必须 resolve 选择保留旧删减版、删除旧删减版或取消此次覆盖，不能默默替用户决定。

下载与预览的正常／原图／删减角色是明确区分的，详见[访问控制](access.md)。

## 加载和失败占位

公开封面只使用指定附件本身：公开附件使用正常表示，机密附件使用同一行的删减表示。没有可用表示时返回空封面并显示占位，不去掉 `.good` 查找另一个同名公开附件；删除删减版或目标附件后也遵守这条规则。

首页封面、档案页头和正文中的档案引用卡片共用封面渲染器与加载状态处理。档案列表和正文接口在封面 URL 旁返回对应表示的尺寸、LQIP，用于提前占位和渐进加载；机密封面只返回可公开删减版自身的元数据，没有删减版时不下发正常图片占位。封面走现有附件入口，按浏览器 Accept 协商 WebP／JPEG，SVG／GIF 等保持原格式。首页保持 eager 加载，避免筛选／排序移动卡片时出现浏览器 lazy load 停滞；本轮未新增首页专用缩略图。

封面和正文图片共用加载状态与动效样式。已处理图片先显示透明度缓慢呼吸的对应版本 LQIP，并提供旋转的加载图标；没有 LQIP 的 GIF／SVG 等也使用加载反馈。图片淡入期间保留其下方的 LQIP，遮罩随之淡出，避免切换时露出底色；系统启用减少动态效果时立即切换。解码失败或引用无效时替换图片区域为占位符，保持原有图片项与 caption 结构。编辑预览增量更新时复用未变化的媒体节点，避免每次输入都重载整篇图片。

## 存量 WebP 维护迁移（2026-11-01）

`20261101133000_content_webp.ts` 是必须显式执行的维护迁移。先停止旧应用／worker，完成或取消在途传输及图片任务，并等待云端草稿租约释放。预检只读；发现未完成任务、失败待重试图片或有效草稿租约即阻止执行，不自动丢弃用户工作。

迁移按附件逐个转换：正常图以当前展示版本为输入，删减图只读取自身当前删减版本，不读取归档原图来重建展示。WebP Q100、JPEG Q85 和 JPEG LQIP 由独立本地 Sharp 维护进程生成，先写私有对象并核验完整 SHA-256、大小及版本，再在一个事务中切换指针、元数据、revision、文件名、正文、封面、引用历史、共享草稿和 outbox。原图归档、已编辑状态、机密标记和来源版本事实保留。

旧另存图片等显式 `.avif` 逻辑文件名转为 `.webp`，保留目录与末尾 `.good`，同名冲突使用数字后缀；上传时保留的 `.png`／`.jpg` 等原始逻辑名称继续保留，与未来上传一致，实际下载名使用 WebP 后缀。迁移新增的 `content_webp_migration_objects` 保留源身份、目标所有权和采用回执；对象写入后事务失败可复用已验证结果，不重复编码。失败停在维护态，完成后才能启动新应用。新迁移将 `avif_key`、`jpeg_key`、`parent_avif_key` 及删减字段改为 `display_key`、`fallback_key`、`source_display_key`、`redacted_display_key`、`redacted_fallback_key`；LQIP 字段改为 `lqip`／`redacted_lqip`，尝试账本同步使用角色名；已结束的历史任务回执仍是历史事实。旧私有展示对象和历史版本暂留，未永久删除，不把代码回退当作数据回退。

只读预检及执行参数沿用[迁移运维](../../operations/migrations.md)：源码环境先以 `pnpm migrate --preflight` 分类待办链，再以 `pnpm migrate --dry-run` 运行当前迁移的只读业务 plan；确认后使用 `pnpm migrate --maintenance`；生产使用同版本维护镜像／备份和既有维护发布流程。不能让旧应用连接已改字段的新库。迁移的真实 MySQL 验证入口为 `pnpm exec tsx --tsconfig scripts/tsconfig.json scripts/verify/webp-migration.ts`，仅创建随机隔离测试库，OSS 使用内存替身。

`content_webp_migration_objects` 的[退出合同](../../operations/migrations.md#webp-回执表64的退出合同)规定生产完成及验收后至少保留 30 日，归档读回、责任交接后才通过独立维护迁移删除；不自动清表，不随回执删除旧对象或释放 pin。下一条旧 Content 退役迁移只删除五张已废弃且为空的旧表，保留本次 WebP 恢复明细。

2026-11-01 生产维护发布已完成上述存量转换和五张旧空表退役，回执表保留；备份、隔离恢复与只读交付验收见[云端台账](../../deployment/aliyun.md#2026-11-01-webp-维护发布与原生持久化权限)。这次维护使用冻结的本地编码器，不代表后续原生持久化代码已经部署。

早先开发桶原生可行性测试中，1536×1024 PNG 生成 WebP Q100 的单次 POST 约 597ms、583,292 字节；该值不含校验、JPEG、LQIP 或发布，不能代表完整适配器耗时。当前原生链路的对照验收如下。

PNG 回退也已按同一份最终 WebP 试验：OSS PNG 为 2,423,705 字节，JPEG Q85 为 287,912 字节。PNG 默认、Q30、Q85 的字节及 SHA-256 完全相同，像素与最终 WebP 一致；[OSS quality 不作用于 PNG](https://help.aliyun.com/zh/oss/user-guide/adjust-image-quality)。本地 PNG 压缩等级 9＋自适应过滤仍为 2,250,401 字节；调色板 PNG 约 864,239 字节，但已减色并损失像素，`quality: 100` 也不是无损。用户据此选择保留 JPEG 回退、优先体积；没有启用 PNG 回退。

早先中转适配器的照片单次约 1.43 秒，历史测量见[记录](../../reviews/webp-feasibility-2026-11-01.json)。本次同机、同桶、相同编码参数比较旧中转和新原生适配器；照片三轮交替先后顺序，其他样本各一轮。完整适配器计时包括持久化、角色校验和 LQIP，不含首次上传、排队、数据库、原图归档或额外验收读取。

| 照片 1536×1024，三轮中位数 | 1,619ms | 1,583ms | 871,204 |
| 半透明 PNG 32×16 | 650ms | 961ms | 408 |

十二次运行的 WebP、JPEG 和 LQIP 均与对应中转结果逐字节一致，透明／白底及方向正确。每份成品匿名 HEAD 为 403，OSS 签名 HEAD 为 200 且 `private, no-store`；两桶 BucketACL 读回均 private。36 个开发测试对象已软删除并确认当前缺失，历史版本保留。另以生产应用身份完成一张未采用的 32×16 合成图原生处理，输出 MIME、版本、私有 ACL 和签名缓存策略通过，三个专用对象同样软删除；未读取现有生产用户对象或写数据库。原生节省了服务器上传带宽，但多次 HEAD／ACL 和一次 SHA-256 回读仍有延迟，小图未见提速；单机小样本不代表生产 p95 或并发收益。脱敏数据见[原生对照记录](../../reviews/oss-native-persistence-2026-11-01.json)。代码发布及真实账号上传／编辑仍待验收。

## 转换性能基线（2026-11-01）

本轮按用户选择先测量，正式画质、处理提供方和云资源均未调整。基线为 #61 后的 `15ac9f4`，使用真实 `process_image_variants`，只在独立基准进程中计时；不连接数据库、不访问生产对象。脚本不进入应用启动或 CI 性能门禁。

### 重复测量

```powershell
$env:NODE_ENV = 'development'
pnpm exec tsx --tsconfig scripts/tsconfig.json scripts/verify/image-performance.ts --output .data/image-performance.json
pnpm exec tsx --tsconfig scripts/tsconfig.json scripts/verify/image-performance.ts --input .data/photo.jpeg --efforts 4,2 --runs 2 --quality --output .data/photo-performance.json
```

输出目录需预先存在。默认顺序处理两张确定性纹理图（1280×800、2400×1600），每个 effort 4／2／0 各运行两次；`--input` 可重复指定自备文件，`--runs` 限制为 1–5。只加载图片配置子树，不需要数据库或云端凭据。报告保留输入 basename、配置、环境、耗时、输出字节、进程 CPU 时间、采样 RSS 和事件循环延迟，不保存转换产物；自行选用不含敏感名称的测试文件。

阶段为源 metadata、AVIF、JPEG、LQIP、最终 metadata。AVIF 阶段包含解码、方向和色彩转换及编码；JPEG／LQIP 阶段各自包含最终 AVIF 的解码，不能把阶段值当作纯编码器耗时。工具委托真实管线，并校验阶段调用数量；管线调整后必须复核标签。`--quality` 另作 sRGB／白底像素 PSNR 诊断，诊断不计入处理耗时，但可能影响后续缓存状态；PSNR 不能代替视觉验收，`null` 表示诊断像素完全一致。

### 排队、I/O 与云端选择

代码确认当前是每 5 秒扫描、图片并发 1、单批最多 20 个任务，扫描期间占用 runner 的 image／OSS 资源槽。长批次处理完才释放，处理中新到任务也不在已有快照里；可感知等待可能同时包含轮询和排队，不能把上述编码时间当作选择文件到最终发布的总耗时。输入下载／Buffer 拼接、两个产物顺序上传、原图归档、数据库采用和预热也未纳入本基准。下一步先记录排队年龄及各外部阶段耗时，再评估入队唤醒和有界批次；数据库池／在线授权延迟目前只是待测风险。

当前 JPEG 与 LQIP 分别解码一次最终 AVIF；effort 降低后这部分占比更高。可实验复用解码，但必须保持二者源自最终 AVIF 的合同，并复测内存和像素。`image-processing.ts` 属于冻结迁移依赖，未来运行时优化需另建入口并按需推进处理 profile；不能直接改历史实现或重算 digest。

阿里云标准 OSS IMG 的[公开限制](https://help.aliyun.com/zh/oss/user-guide/overview-17/)为原图不超过 20MB、AVIF 输出宽不超过 4096px 且总像素不超过 9,437,184。当前应用接受 50MiB／2400 万像素，上述 3924×2550 照片也超过标准 AVIF 像素限制，因此不能直接全量替换；需本地回退、其他计算服务或工单确认更高限额。下述试验按用户要求先忽略尺寸边界比较速度，不代表已经解决这些接入限制；费用尚未核定。

若选云端持久化处理，还须保留私有对象、尝试身份／租约、完整角色后原子采用及迟到结果清理；JPEG／LQIP 仍须从最终 AVIF 派生。[sys/saveas](https://www.alibabacloud.com/help/en/oss/user-guide/sys-or-saveas)需要来源处理权限及目标写权限，输出继承目标桶 ACL，不能用公开转换 URL 绕过当前读取授权。

**转换调用的隔离要求：** 用户明确要求普通用户不能获得云端转换入口。本轮测速使用私有源对象和 300 秒有效期的 OSS V4 预签名 GET，处理参数参与签名，URL 仅通过 SSH stdin 传入独立服务器进程，不返回浏览器、不记录完整签名 URL。预签名 URL 是有效期内持有即能使用的凭据，不能仅靠过期时间实现用户隔离。后续正式接入只允许后台以服务端凭据调用固定处理参数／受控来源与目标，优先 SDK 请求头鉴权；不提供任意对象、参数或 URL 的签名／转换 API，不把转换 URL 放入接口响应、重定向或页面。持久化目标桶必须确认私有，因为 `sys/saveas` 产物继承目标桶 ACL；全部角色回执和权限验证后，用户继续通过现有 Content／ESA 读取鉴权访问成品。现有 ESA 参数白名单拒绝 `x-oss-process`（包括 style），不能为了接入云端转换而放行或透传；正式上线前仍需验证匿名直连拒绝、参数篡改拒绝和前端无转换凭据。

开发身份最初执行 `sys/saveas` 返回缺少 `oss:PostProcessTask` 的 HTTP 403。用户为本轮随机前缀补权限后，两次真实 AVIF 请求返回 HTTP 400、`BadRequest`、`Avif encode is not supported.`。因此不能把 GET 支持 AVIF 推导为该 endpoint 的 `sys/saveas` 也支持；正式实现改用后台 IMG GET + 私有 PUT，不需要扩展现有 RAM 策略。本轮原生持久化试验的临时源和哨兵均已软删除，预登记目标也逐一删除并确认当前 404；历史版本保留。该临时权限现可由用户撤销，代理未执行 RAM 管理操作。

本轮 GET 试验没有改应用配置、写数据库或读取既有生产附件。两份临时源对象均已软删除，当前 HEAD 确认 404；旧版本仍由桶的实际生命周期保留，没有永久删除或扩大版本删除权限。返回的测试产物与摘要保存在本机忽略目录，不提交图片到仓库。

### OSS 与 Sharp 的质量刻度对照

这不是通用的质量乘数。2026-11-01 用三份不透明 sRGB 样本诊断：用户照片（1536×1024）、官方照片的缩小版（2400×1560），以及确定性的高饱和彩色细网格（1024×768）。输入先规范为无损 PNG，避免解码、方向或源 JPEG 的质量估计干扰；官方照片另以原 JPEG 做 Q65／97／100 对照，三个输出均与规范 PNG 输入时字节相同。逐档数据、输入摘要、码流采样及校验结果见[测量摘要 JSON](../../reviews/image-quality-mapping-2026-11-01.json)。

| 角色 | 当前 Sharp 参数 | 本轮 OSS 对照 | 适用边界 |
| --- | --- | --- | --- |
| AVIF | quality 65、effort 4、默认 4:4:4 | 两张照片的目标 PSNR 落在 OSS Q96／Q97 两档之间；Q97 是达到或超过目标的最小已测档位 | 不是精确等画质，也不适用于全部图像；彩色网格 Q100 仍达不到 Sharp 65 |
| JPEG 回退 | quality 85、默认 4:2:0 | Q85 | 相同最终 AVIF 输入时，量化表、解码像素与编码数据一致，仅 OSS 增加 18 字节 JFIF APP0 头 |
| LQIP 编码 | quality 40、24px JPEG | Q40 | 同一份已缩小 PNG 输入时与 Sharp 编码一致；OSS 自己缩放及上游 AVIF 的差异另算 |

#### AVIF：照片的近似档位与颜色边界

两张照片都观察到以下 PSNR 区间，不能据此插值出严格等价的 Q，也不能外推到未测图片或其他编码器版本：

| Sharp quality（effort 4、4:4:4） | OSS 已测 PSNR 对照 |
| --- | --- |
| 30 | Q20 已高于目标，本轮未向更低档位标定 |
| 40 | 目标介于 Q50 和 Q60 之间 |
| 50 | 目标介于 Q85 和 Q90 之间 |
| 65 | 目标介于 Q96 和 Q97 之间 |
| 75、85 | Q100 仍低于目标，没有达到目标的已测档位 |

当前 quality 65 的具体结果：

| 样本 | Sharp 65 PSNR | OSS Q94／95／96 PSNR | OSS Q97／98／100 PSNR | Sharp 65 → OSS Q97 字节 |
| --- | --- | --- | --- | --- |
| 用户照片 | 39.21 dB | 38.17 dB | 40.44 dB | 137,267 → 180,251（约 +31%） |
| 官方照片 | 40.38 dB | 39.20 dB | 41.45 dB | 198,228 → 272,679（约 +38%） |
| 彩色细网格 | 39.84 dB | 29.44 dB | 29.90 dB | 38,118 → 107,001，仍低于目标 |

三张图在本次路径中分别出现 Q60／65、Q94／95／96、Q97／98／100 返回完全相同字节的档位组。这是实测现象，不推断云端内部如何量化或缓存；不能把 Q97 提到 Q100 当作必然的画质提升。

依据 [AV1 配置记录](https://aomediacodec.github.io/av1-isobmff/#av1codecconfigurationbox-syntax)解析实际 AVIF 的 `av1C`：Sharp 当前输出 profile 1、8bit、4:4:4，符合 [Sharp 的默认选项](https://sharp.pixelplumbing.com/api-output/#avif)；本次 OSS Q65／97／100 则均为 profile 0、8bit、4:2:0。色度采样会影响彩色细线与边缘，提高 Q 不能直接恢复已减少的色彩采样。独立把 Sharp 65 改为 4:2:0 后，网格 PSNR 从 39.84 降至 33.20 dB，仍高于 OSS Q100 的 29.90 dB，因此差异不只由采样解释，不能把固定比例当成质量合同。本轮没有验证能将 OSS 输出切为 4:4:4 的公开参数，也未改正式采样设置。

#### JPEG 与 LQIP：先隔离编码，再看完整链路

JPEG 对照的两端都读取同一份最终 Sharp AVIF；LQIP 编码对照读取同一份由该 AVIF 缩到最大 24px、白底的无损 PNG。JPEG 的 40／65／75／85／95、LQIP 的 20／40／60，各在三张图验证，共 24 组：同档位量化表与 4:2:0 采样一致，解码像素逐字节相同；移除 JFIF APP0 后其余 JPEG 文件也逐字节相同。本轮可将编码参数按 1:1 对照，但不保证其他版本或不同选项永远如此。Sharp 直接从 AVIF 缩放并输出 quality 40 的 LQIP，也与经共享 PNG 再编码的三份结果逐字节一致，确认该中间步骤未改变本轮对照。

完整 LQIP 还有缩放差异：同一最终 AVIF 经 OSS 与 Sharp 各自缩成无损小图，两张照片的 RGB PSNR 仅约 31.78／29.04 dB；加入 Q40 JPEG 后，与 Sharp 缩放参考的 PSNR 分别为 23.17／21.25 dB，而 Sharp 原链路为 23.85／22.03 dB。不能为了补缩放误差，直接把 JPEG Q 当作补偿系数。JPEG 回退同样会继承各自 AVIF 的误差：参数 85 对应 85 不代表不同 AVIF 输入最终生成相同图片。

上述质量标定只验证 GET 转换和本机像素／码流，不把 PSNR 当作视觉等价证明，也不证明透明图、ICC／HDR、其他尺寸或全部输入格式的质量合同。标定新增的 22 个私有测试对象均已软删除，当前 HEAD 为 404；历史版本未永久删除。后续接入与透明图验收另列于下文。

### 后台接入验收（2026-11-01）

真实运行 `create_oss_image_processor`，使用开发桶的本轮独占 UUID staging／image keys，不写业务数据库，不接触既有附件。两轮各测试用户照片、全透明 PNG、EXIF orientation 6 JPEG；均完成 AVIF／JPEG 的私有 PUT、版本／大小／SHA-256 回读核对，以及从最终 AVIF 生成的 LQIP。[脱敏验收摘要](../../reviews/oss-image-integration-2026-11-01.json)保留输入／产物摘要与最后一轮计时。校正计时边界后的单轮结果如下，调用客户端为本机 ARM64，计时不包含后续人工式回读／匿名请求断言：
