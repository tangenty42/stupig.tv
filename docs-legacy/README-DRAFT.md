## 目的与基本分工

本机制分别记录以下内容：

| 内容 | 回答的问题 | 维护责任 |
| --- | --- | --- |
| `LAWS.md` | 业务应该怎样，用户会看到什么，怎样才算验收通过 | 人类实际编写、核对和修改；agent 只提供建议 |
| `DESIGN.md` | 实现必须遵守什么架构、组织形式和工作传统，为什么 | 人类实际编写、核对和修改；agent 只提供建议 |
| agent 实现说明 | 当前如何实现，与规范有哪些对应关系和偏差 | agent 根据源码、配置与验证证据维护 |
| agent 工作记录 | 正在推进什么，哪些问题待定，下一步由谁处理 | agent 维护事实、建议和进度；不能自行形成规范 |
| 验证证据 | 哪个版本、在哪个环境、检查过什么 | 自动检查与人工验收分别记录，保留证据及未验证范围 |

`LAWS.md` 与 `DESIGN.md` 是权威文件，草稿也由人类维护。禁止 agent 自动改写、格式化、移动、删除或通过生成器覆盖它们；权威文档明确引用为验收依据的图片等资产同样保护。agent 可以在聊天或建议区提供结构、候选措辞、差异分析和校对意见，由人类写入文件。

规范定义应有行为；代码、经过核验的配置和运行证据说明实际行为。两者不一致时记录偏差，不能为了与代码一致而修改规范，也不能仅凭规范文字声称已经实现。实现说明应随事实更新，规范的改变须由人类决定并写入。

## 目录组织

目录表达主题，文件名表达权威与用途。目标结构如下，未列出的领域和工作流程按实际需要扩展：

```text
docs/
├── README.md
├── 0_overall/
│   ├── 0_background/
│   ├── 1_dependencies/
│   └── 2_conventions/
├── 1_workflows/
│   ├── 0_development/
│   └── 1_deployment/
└── 3_domains/
    ├── 0_index/
    │   ├── p0_home/
    │   └── p1_about/
    └── 1_content/
        ├── c0_previewer/
        ├── c1_editor/
        ├── p0_home/
        ├── p1_detail/
        └── p2_edit/
```

- `0_overall` 记录背景、依赖选择和共同约定。依赖文档说明选型原因、兼容与升级约束，完整版本以包管理和配置文件为准。
- `1_workflows` 记录开发、测试、部署、恢复等工作流程。流程的前提、责任和成功条件放在 LAWS，工具链、执行机制和恢复设计放在 DESIGN。
- `3_domains` 按功能领域组织。领域目录负责共享业务规则，`p` 表示页面，`c` 表示可复用功能组件；两类分别编号。
- 组件是值得独立定义和验收的功能单元，不必与单个 Vue 文件对应。普通内部包装、按钮或工具函数无需各建一个文档目录。
- 各主题目录按需放置 `LAWS.md`、`DESIGN.md` 和 agent 文档。没有内容时不创建空文件，不要求每层凑齐全部类型。
- 同一个规则只由一个位置负责。例如草稿与正文的关系由 Content 领域负责，编辑器负责输入交互，编辑页负责组合、导航和页面生命周期。其他位置引用规则并补充自身要求。

### 编号与引用

文档标识由目录编号和文件类型组成，用点连接；保留 `p`、`c` 前缀，省略目录的文字后缀和 `.md`：

| 路径示例 | 文档标识 |
| --- | --- |
| `3_domains/LAWS.md` | `3.LAWS` |
| `3_domains/1_content/LAWS.md` | `3.1.LAWS` |
| `3_domains/1_content/c1_editor/DESIGN.md` | `3.1.c1.DESIGN` |
| `3_domains/1_content/p2_edit/LAWS.md` | `3.1.p2.LAWS` |
| `1_workflows/1_deployment/DESIGN.md` | `1.1.DESIGN` |

`docs/README.md` 是机制入口，直接按路径引用，不分配业务编号。若在 `docs/` 根目录设置权威文件，其标识分别为 `LAWS`、`DESIGN`，作为根级规范。

编号是稳定地址，不是阅读顺序。新增主题使用未占用的编号，不为插入或排序重新编号；根目录暂不使用 `2`。目录文字后缀可以在人类安排的迁移中调整，但须修正链接。跨父目录移动会改变标识，必须核对引用并保留旧标识到新标识的映射；不回收已使用的标识。

重要业务规则使用 `R010` 一类编号，验收条件使用 `R010-AC01`，设计决策使用 `D004`。编号只在所属文档内唯一，不与章节顺序绑定；简单说明无需逐句编号。删除或替代条款时保留简短的退役或替代说明，不把旧编号赋予另一条要求。

完整引用示例：`3.1.p2.LAWS#R010`、`3.1.p2.LAWS#R010-AC01`、`3.1.c1.DESIGN#D004`。条款使用显式 HTML 锚点，避免改标题导致引用失效。实际文档之间使用相对 Markdown 链接，链接文字带完整标识；纯标识用于讨论和检索，不能假定平台已经提供自动解析功能。

### 适用范围与冲突

1. 祖先目录的生效规范适用于其子目录；下级规范补充细节，不能默认覆盖上级要求。
2. 兄弟目录之间不自动继承。页面使用组件、领域依赖其他领域时，明确引用相关规范并说明关系。
3. `0_overall` 与其他目录是兄弟目录。需要全项目生效的条款必须明确标注全项目范围，并由各阅读入口纳入；不能只凭 `overall` 名称推断约束范围。
4. DESIGN 必须满足适用的 LAWS。重要例外由人类明确写出所例外的条款、适用范围、原因及生效条件。
5. agent 说明、工作记录、实现结果和测试结果不能覆盖权威规范；“已经做过”不等于“以后必须这样做”。
6. 规范之间冲突或关键行为缺失时，记录问题和影响，交由人类裁决；继续不依赖该决定的工作，不自行选择更方便的解释。

## 文档头与状态

权威文档以简短说明区确定身份和范围。以下示例只展示格式：

```markdown
# 档案编辑页

- 标识：3.1.p2.LAWS
- 状态：草案
- 范围：已有档案和未发布草稿的编辑页面
- 上级规范：3.1.LAWS（领域业务规则）
- 相关规范：3.1.c1.LAWS（使用编辑器交互合同）
- 不包含：附件上传协议、编辑器内部实现
- 生效依据：尚未核定
```

正式文件中的规范引用应补成实际可访问的链接。作者和一般修改时间由 Git 记录，不手工维护重复时间表。

| 状态 | 含义 |
| --- | --- |
| 草案 | 尚待人类核定，不替代既有生效要求 |
| 生效 | 人类已核定，注明适用条件和可追溯的决定依据 |
| 已替代／退役 | 保留历史依据和替代引用，不继续作为当前要求 |

状态由人类更新。规范生效不等于代码已经实现或上线；生效范围可以绑定明确的版本或切换条件。草案可以包含未决问题，生效文档中仍未决定的部分必须明确划出，不能由 agent 补成默认要求。

正文明确区分“要求”“解释／示例”和“未决问题”。示例用于说明条款，不隐含额外义务；尚待决定的建议不混在强制要求中。

## LAWS 的编写方式

LAWS 围绕可观察行为和验收组织。建议结构如下，按文档性质删减，不机械填表：

```text
目的与范围
术语与角色
状态与操作
业务规则（按主题组织，验收条件紧邻对应规则）
界面清单与变更边界（有 UI 时）
整体体验与跨场景验收
```

每条重要规则写清适用条件、触发动作、预期结果和必要的失败／恢复边界。验收以身份、初始状态、操作和可观察结果消除歧义。涉及时间或规模时写明条件及允许范围，不使用无法验收的“及时”“友好”等词替代要求。

下面是条款写法示例，不作为本机制新增的业务决定：

```markdown
## 自动保存与正式发布

<a id="R010"></a>
### R010 自动保存不得发布正文

适用条件：当前页面持有有效编辑权。

要求：自动保存只更新云端草稿；公开详情页继续展示最后一次正式发布的正文。

<a id="R010-AC01"></a>
#### R010-AC01 草稿与正文分别验收

已有正式正文 A。用户输入 B，等待草稿保存成功。
重新读取草稿应得到 B；公开详情页仍应展示 A。

<a id="R010-AC02"></a>
#### R010-AC02 保存失败

草稿保存失败时，不得显示保存成功。
页面保留尚未确认的输入，并按已规定的失败状态提示用户。
```

复杂交互先用状态表或状态图说明“当前状态、事件、后续状态、用户可观察结果”，再引用具体条款处理例外。覆盖相关的正常、加载、空数据、失败、无权限、取消和恢复状态，不要求每个主题机械覆盖所有组合。

LAWS 固定验收含义；测试文件、选择器、执行命令和覆盖映射由 agent 实现说明维护。业务输入输出格式、可接受的等待边界等本身属于合同的细节仍应明确，不能因其带有技术形式而省略。

## UI 清单与变更边界

用户可见的部件、文案、状态、布局要求和交互逻辑属于 LAWS。组件选型、主题 token、布局机制和状态管理属于 DESIGN。页面清单可以引用领域或公共组件清单，只补充本页的模式和组合要求。

### 封闭清单

生效的 UI 清单采用封闭原则：agent 不得自行新增具有用户语义的区域、控件、文案或交互步骤。按钮、入口、菜单、提示卡片、徽标、教程、占位文案、确认弹窗、通知和状态表达都属于这一范围。删除或改变已规定的部件同样需要规范依据。

“让用户更清楚”“看起来更完整”“更安全”不能自行成为增加提示或确认的理由。已有公共组件并不授权在新场景中增加一个部件；使用允许的组件和符合界面清单必须分别满足。

建议清单包含以下字段。每行使用稳定的部件标识或关联规则编号，方便状态表、截图和验收引用；以下仅为格式示意：

| 部件／规则 | 区域与位置 | 表达约束 | 显示与可用条件 | 动作及反馈 |
| --- | --- | --- | --- | --- |
| 正式保存按钮／对应条款 | 页面操作区，顺序明确 | 固定文案“保存” | 引用编辑权和保存状态条款 | 发布正文，成功与失败分别引用反馈条款 |
| 保存状态区／对应条款 | 正文编辑区域旁 | 仅使用状态表列出的表达 | 随明确状态变化 | 不附加建议、入口或技术说明 |
| 舍弃草稿入口／对应条款 | 规定的菜单或操作区 | 文案和确认内容明确列出 | 按草稿状态规定 | 确认、取消和失败各有定义 |

除静态部件外，还要说明需要约束的交互：焦点、键盘、滚动、窄屏排列、加载与空状态、失败提示的位置、操作是否阻塞、是否允许重试以及重试由谁触发。动画、深浅色和减少动态效果等只在相关主题中规定，不为每个文件重复整套要求。

清单不允许 agent 自动删掉迁移前未登记的既有 UI。迁移时先盘点差异，由人类决定保留、修改或移除，再形成生效清单。对规范未覆盖的新情况提出建议，不能擅自实现，也不能擅自删掉原有失败处理。

### 固定内容与允许调整的范围

| 级别 | 内容示例 | agent 可做什么 |
| --- | --- | --- |
| 固定 | 控件是否存在、准确文案、操作顺序、确认步骤 | 按规范实现，不自行改写或增删 |
| 有界调整 | 既定间距档位、允许的换行、窄屏排列方式 | 在明确列出的范围内选择 |
| 实现细节 | 无可见影响的 DOM 包装、内部拆分 | 遵守 DESIGN 自主处理 |

文案逐项注明“逐字固定”“数据生成且格式固定”或“允许在指定含义内调整”。未声明可改写的已给定文案按固定内容处理；尚未提供的必要文案作为待决策项，不由 agent 自行润色补全。可访问名称、提示和校验错误等用户会感知的表达也适用。

截图或原型须注明适用状态、视口、主题以及哪些细节属于验收要求。示意图片不隐含所有像素都必须一致；权威截图的修改与替换由人类维护。

### UI 验收

- 可见部件和文案能对应清单或明确引用的公共规范，没有未批准的新增表达。
- 加载、空数据、失败、无权限和恢复等相关状态符合各自定义。
- 操作没有额外引入确认、跳转、通知、自动重试或其他未规定的步骤。
- 布局、焦点、滚动及响应式变化在允许范围内，功能组合不破坏组件合同。
- 自动检查和人工走查分别记录。更新截图基线不能代替对 UI 变化的人工核定。

## DESIGN 的编写方式

DESIGN 记录重要实现决定、理由、代价和允许的变化范围。建议结构如下：

```text
设计目标与约束
职责与边界
结构与协作关系
关键设计决策
关键运行流程
故障、兼容与演进约束
```

每项重要决策对应适用的 LAWS 条款或工程约束，说明为什么采用该方案、必须保持什么、哪些部分允许 agent 自主调整。不能完全由业务推导的外部平台限制、资源预算和恢复要求，也要说明依据。

```markdown
<a id="D004"></a>
## D004 分离草稿保存与正文发布

对应要求：3.1.p2.LAWS#R010。

决定：草稿保存与正文发布使用明确区分的命令与状态；发布前验证待发布的草稿版本。

理由：草稿保存成功不能使未正式发布的输入对读者可见。

代价与限制：需要分别处理两类命令的结果未知、版本变化和反馈。

实现自由：允许调整内部函数拆分，不得合并两类命令的业务含义。

验证要求：覆盖自动保存后正文不变，以及发布过期草稿版本时的规定行为。
```

此例只演示决策写法。文件名、类名和调用链只有在其本身属于组织约束时才进入 DESIGN；当前落点由 agent 实现说明负责，避免人类逐次追赶内部重构。

UI 设计可列出确认、通知、表单、菜单等功能应复用的现有组件，允许的主题值、局部样式边界和新建共享组件的条件。重要决策改变时保留原理由及替代关系，不把旧决策改写成从未发生。

## agent 文档与证据

agent 文档文件名仍待人类确定。`IMPLEMENTATION.md` 和 `WORK.md` 仅是候选名称，不据此自动创建目录或文件。无论采用何种命名，内容分工如下：

| 实现说明 | 工作记录 |
| --- | --- |
| 对应规范、源码或配置基线 | 事项标识与关联条款 |
| 当前入口、职责和运行方式 | 问题、证据和影响 |
| 条款到实现、测试的对应关系 | 建议、备选方案及取舍 |
| 已知偏差、未覆盖和未核验范围 | 下一步责任方、阻塞原因与完成条件 |
| 验证与发布证据链接 | 当前状态及决定依据 |

实现说明按主题更新，不复制完整规范。工作记录只维护仍需行动的事项，完成后保留结果链接并归档，不在每个任务结束时新增阶段报告。已经由人类明确决定的事项引用原决定，不重复征询；未决定的建议不能写成既定传统。

“已实现”“自动检查通过”“人工验收通过”“已部署”分别记录，不能用单个“完成”替代。证据至少说明代码或产物版本、环境、身份／前提、动作、结果和未验证范围。没有核对线上配置，不写成“已配置”；本地测试和 PR 合并不证明生产已交付。

一次性日志、临时对象名和进程信息留在本次验证产物或 PR 中，长期文档保留有用结论和引用。涉及外部材料时提供来源；文档与证据均不写凭据、完整签名链接或不必要的个人数据。

## 人机协作与变更流程

1. **确定范围。** 阅读本文、适用的全局与祖先规范、当前主题的 LAWS／DESIGN，以及明确引用的页面／组件合同；再查实现说明、源码和测试。
2. **整理依据。** agent 区分人类已有决定、代码现状和待验证假设，列出缺口、矛盾及必要的方案建议。不能把从代码提取的行为直接提升为业务规则。
3. **人类编写。** 人类实际编写并核对 LAWS、DESIGN 和权威 UI 资产。agent 协助总结、检查歧义、寻找遗漏场景，建议留在聊天或建议区。
4. **实施与验证。** 在已确定的业务和设计边界内，agent 自主处理实现细节、编写测试并记录证据。新增业务行为或改变重要约束时，先交回人类决定与修订。
5. **核对验收。** 按条款检查实现与 UI 清单，区分自动验证、人工体验验收和外部环境验证。agent 不替人类宣布体验已验收。
6. **维护现状。** agent 更新实现说明、偏差与事项状态；人类更新规范状态和决策。需要部署或迁移时继续遵守相应操作授权，不把文档决定等同于生产操作授权。

文案、格式和低风险说明变更不要求仪式性测试。测试由风险和合同决定；agent 可以重构测试代码，但不能为了通过检查而删除有价值的验收场景、放宽业务断言或更新视觉基线来掩盖偏差。

## 保护与检查

本文规定的是维护责任，不能单靠文件名或文字形成技术上的写入隔离。严格保护需要后续落实 agent 对权威区域的只读访问、与人类分离的写入权限，以及相应的合入检查；这些措施目前不因本稿而宣称完成。格式化工具、生成器和 hooks 也应避开权威文件，保护配置自身同样需要受控维护。

轻量检查可以核对文档标识、条款编号、链接、锚点、保护区域变更和规范到验证的映射；人类审查负责判断业务含义、设计取舍和 UI 表达是否正确。自动检查无法代替该判断。

本次机制起草不变更现有工具和指令。过渡期继续按[项目规则](../.github/copilot-instructions.md)与[文档风格规则](../.github/instructions/code-style.instructions.md)执行 lint、链接及来源一致性检查。后续接入保护时，要处理当前自动修复入口，不能只在规范中声明只读。

重写或移动旧材料前核对历史，保留作者的 POV、排障故事、个人表达与配图。已有[保护标记](../.github/instructions/code-style.instructions.md#protected-content-markers)及其授权要求继续适用，不因文档迁移失效。

## 过渡与待定事项

本稿先建立可核对的机制，不批量重命名或改写其他文档。旧手册暂时继续提供实际操作说明，不能因本稿出现而自动失效，也不能自动改名成为人类权威规范。

建议按业务主题逐步迁移：盘点旧资料及依据 → 人类编写规范 → 核对现有实现与验收 → 整理 agent 说明 → 更新引用。旧规则由新规范替代时注明范围与替代关系；不能同时留下两份互相冲突的现行要求。尚未编写新规范的区域继续遵守已有规则，遇到实质歧义交由人类裁决。

以下内容仍待确定，不由 agent 在执行中自行补齐：

- agent 文档的最终文件名、建议区位置和归档方式。
- 首批迁移主题，以及各主题规范的生效与切换条件。
- 权威文件的实际写入隔离、合入保护和自动格式化排除机制。

现有 [AGENTS.md](../AGENTS.md) 与 [.github 指令](../.github/copilot-instructions.md)保持工具入口职责。迁移时让入口引用本文及相应规范，不在入口、工作传统和操作手册中重复维护整套文档机制。
